Backend For Frontend (BFF)

Arquitectura de Seguridad Multicapa

Santiago Fernández

Arquitectura aplicable a fintech, e-commerce, salud, SaaS, logística...

❌ El Problema: Arquitectura Insegura

Frontend → Microservicio Saldo (directo)
Frontend → Microservicio Usuario (directo)
Frontend → Microservicio Préstamos (directo)
Frontend → Microservicio Tarjetas (directo)
  • ⚠️ Superficie de ataque amplia
  • ⚠️ Sin control centralizado
  • ⚠️ Gestión de tokens compleja
  • ⚠️ Múltiples llamadas = alta latencia

✅ La Solución: Backend For Frontend

Usuario → Frontend → BFF → Microservicios
⬇️
Keycloak (CIAM)

✓ Punto único de entrada

Todas las peticiones pasan por el BFF

✓ Validación centralizada

Tokens, permisos, rate limiting

✓ Agregación de datos

El BFF combina respuestas

✓ Microservicios protegidos

Solo el BFF puede acceder

Capa 1: OAuth2 + OIDC

1. Usuario → Frontend: Click "Login"
2. Frontend → Keycloak: Redirect
3. Usuario → Keycloak: Credenciales
4. Keycloak → Frontend: Authorization Code
5. Frontend → Keycloak: Code + PKCE
6. Keycloak → Frontend: Access Token + Refresh Token

Capa 2: PKCE en el Frontend

// Frontend - Keycloak config const keycloak = new Keycloak({ url: 'http://localhost:8080', realm: 'financial-banking', clientId: 'frontend-banking', }) // Inicializar con PKCE await keycloak.init({ onLoad: 'check-sso', pkceMethod: 'S256', // ✅ SHA-256 })

¿Por qué PKCE?

Sin PKCE, un atacante podría interceptar el authorization code. PKCE añade un code_verifier que solo el cliente conoce.

Capa 3: Doble Validación de Tokens

🔑 La clave de la seguridad del BFF

Token 1: User Token

Header: X-User-Token eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...

Indica quién es el usuario

Token 2: Service Token

Header: Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...

Indica que viene del BFF

Seguridad: Si un atacante roba el User Token, no puede usarlo directamente contra los microservicios. Necesita también el Service Token que solo tiene el BFF.

BFF: Obtener Service Token

// BFF - Obtener Service Token (Client Credentials) export const getServiceToken = async () => { const response = await axios.post( `${keycloakUrl}/realms/${realm}/protocol/openid-connect/token`, new URLSearchParams({ grant_type: 'client_credentials', client_id: 'bff-banking', client_secret: process.env.BFF_CLIENT_SECRET, }) ) return response.data.access_token } // BFF - Llamada a microservicio const response = await axios.get('http://saldo-service:3001/api/saldo/cuentas', { headers: { 'Authorization': `Bearer ${serviceToken}`, // Token del BFF 'X-User-Token': userToken, // Token del usuario } })

Microservicio: Validación Doble

// Middleware 1: Validar Service Token const validateServiceToken = (req, res, next) => { const token = req.headers['authorization']?.replace('Bearer ', '') jwt.verify(token, getPublicKey(), (err, decoded) => { if (err) return res.status(401).json({ error: 'Invalid token' }) // Verificar que es el BFF if (!decoded.azp === 'bff-banking') { return res.status(403).json({ error: 'Unauthorized service' }) } next() }) } // Middleware 2: Validar User Token const validateUserToken = (req, res, next) => { const userToken = req.headers['x-user-token'] jwt.verify(userToken, getPublicKey(), (err, decoded) => { req.user = decoded // Datos del usuario para RBAC next() }) }

Capa 4: mTLS (Mutual TLS)

Los microservicios solo aceptan conexiones del BFF usando certificados mutuos

// BFF - Cliente HTTP con certificados const saldoClient = axios.create({ baseURL: 'https://saldo-service:3001', httpsAgent: new https.Agent({ cert: fs.readFileSync('/app/certs/bff.crt'), key: fs.readFileSync('/app/certs/bff.key'), ca: fs.readFileSync('/app/certs/ca.crt'), rejectUnauthorized: true, // ✅ Verificar certificado }) })

Cada servicio tiene su propio certificado firmado por nuestra CA. Solo conexiones con certificado válido pueden comunicarse.

Capa 5: Rate Limiting

import rateLimit from 'express-rate-limit' const limiter = rateLimit({ windowMs: 15 * 60 * 1000, // 15 minutos max: 100, // 100 requests por ventana message: { error: 'Too Many Requests', message: 'Demasiadas peticiones, intenta más tarde.', }, standardHeaders: true, }) app.use('/api/', limiter)

Protección contra ataques de fuerza bruta y abuso. Máximo 100 requests cada 15 minutos por cliente.

Capa 6: Circuit Breaker

CLOSED: Todo funciona normalmente
OPEN: Servicio falla, se bloquean peticiones
HALF-OPEN: Probando si el servicio se recuperó
const breaker = new CircuitBreaker(asyncFunction, { timeout: 5000, // 5 segundos errorThresholdPercentage: 50, // Abrir tras 50% errores resetTimeout: 30000, // Reintentar tras 30 seg })

Capas 7 y 8: Security Headers + CORS

Helmet (Security Headers)

app.use(helmet({ contentSecurityPolicy: { ... }, hsts: { maxAge: 31536000, includeSubDomains: true, }, }))
  • X-Frame-Options: DENY
  • X-Content-Type-Options: nosniff

CORS Restrictivo

const allowedOrigins = [ 'http://localhost:5173' ] app.use(cors({ origin: (origin, callback) => { if (allowedOrigins.includes(origin)) { callback(null, true) } }, credentials: true, }))

Capa 10: Input Validation con Zod

import { z } from 'zod' const SaldoQuerySchema = z.object({ userId: z.string().uuid(), periodo: z.enum(['dia', 'semana', 'mes', 'año']).optional(), limit: z.number().min(1).max(100).optional(), }) app.get('/api/saldo', async (req, res) => { try { const query = SaldoQuerySchema.parse(req.query) // ✅ Query validado y tipado const saldo = await getSaldo(query.userId, query.periodo) res.json(saldo) } catch (error) { if (error instanceof z.ZodError) { return res.status(400).json({ error: 'Invalid input', details: error.errors, }) } } })

🔄 Flujo Completo: Dashboard Request

1. Usuario accede /dashboard
2. Frontend → BFF (user token)
3. BFF valida user token ✅
4. BFF verifica rate limit ✅
5. BFF obtiene service token
6. BFF → 4 microservicios en paralelo (circuit breaker)
7. Cada microservicio: valida service token + user token ✅
8. BFF agrega respuestas
9. BFF aplica data masking en logs
10. Frontend recibe dashboard completo

📝 Compliance: PCI DSS

Para aplicaciones financieras que manejan tarjetas:

✓ Nunca almacenar CVV/CVC
✓ Encriptación en tránsito (TLS 1.3 + mTLS)
✓ Encriptación en reposo (PostgreSQL)
✓ Logging y auditoría completa
✓ Segregación de redes (Docker)
✓ Rate limiting (anti brute-force)
✓ Strong authentication (OAuth2)
✓ Soporte MFA (Keycloak)

💾 Database Per Service Pattern

Saldo Service → PostgreSQL (saldo_db)
Usuario Service → PostgreSQL (usuario_db)
Préstamos Service → PostgreSQL (prestamos_db)
Tarjetas Service → PostgreSQL (tarjetas_db)
  • ✓ Independencia entre servicios
  • ✓ Escalado independiente
  • ✓ Fallo aislado (resilencia)
  • ✓ Diferentes tecnologías si es necesario

🎯 Puntos Clave

  • ✓ Nunca exponer microservicios directamente al frontend
  • ✓ Doble validación de tokens: user token + service token
  • ✓ mTLS para comunicación service-to-service
  • ✓ Rate limiting y circuit breakers para resiliencia
  • ✓ Logging con data masking para compliance
  • ✓ Input validation en todos los endpoints
  • ✓ Security headers y CORS restrictivo
